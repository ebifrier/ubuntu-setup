# Codex Review

Codex CLI（`codex exec review`）に変更をレビューさせ、指摘を確かめて直し、指摘が尽きるまで再レビューする。
Codex は読むだけ。修正・検証はこのセッションで行う（Codex の sandbox では DB やネットワークに届かないことがあるため）。

## 1. 対象を決める

引数があればそれに従う。無ければ次で決める。

| 状況                                                       | 対象                         |
| ---------------------------------------------------------- | ---------------------------- |
| 既定ブランチ以外にいて、既定ブランチより先にコミットがある | `--base <既定ブランチ>`      |
| それ以外で未コミットの変更がある                           | `--uncommitted`              |
| どちらも無い                                               | 「レビュー対象なし」で終える |

既定ブランチは `git symbolic-ref --short refs/remotes/origin/HEAD`（`origin/` を除く）、取れなければ `main`。
`--base` は merge-base と作業ツリーを比べる（`git diff <merge-base>`）ので、周回中の未コミットの修正も次の周で見られる。
周回数の既定は 3。

## 2. レビューを走らせる

1 回に数分〜10 分以上かかる（reasoning effort high で約 8 分）。Bash の `run_in_background: true` で走らせ、完了の通知を待つ（ポーリングしない）。

出力の置き場所 `D` は scratchpad。無ければ最初の周で `mktemp -d /tmp/codex-review.XXXX` を作り、全周で使い回す。

```bash
OUT=$D/codex-review-<N>.md
LOG=$D/codex-review-<N>.log
codex exec review <対象> --ephemeral -c sandbox_mode='"read-only"' -o "$OUT" > "$LOG" 2>&1 < /dev/null; echo "exit=$?"
```

- `sandbox_mode` を `read-only` にする（既定の `workspace-write` だと Codex がファイルを書き換えられる）。

- 読むのは `$OUT`（最終的なレビュー結果）だけ。`$LOG` は Codex が読んだファイルの中身まで流れて 100KB を超えるので、失敗したときに `tail -n 40` で見るだけにする。
- `--base` / `--uncommitted` / `--commit` と独自の指示（PROMPT 引数）は併用できない。観点を足したいときは PROMPT だけで渡し、指示の中で対象の差分（例: `git diff $(git merge-base main HEAD)`）を明示する。
- 結果の冒頭に「テストは読み取り専用環境で実行できなかった」と書かれるのは read-only のせいで、問題ない（検証は 4 でこちらが行う）。
- `exit` が 0 以外、または `$OUT` が空なら、`$LOG` の末尾を示してユーザーに報告し、止める（認証切れ・使用量の上限など、こちらで直せないことが多い）。

## 3. 指摘を仕分ける

**REQUIRED SUB-SKILL:** superpowers:receiving-code-review の流儀で、指摘を一つずつコードで確かめる。うのみにしない。

| 判定 | 条件                                                                     | 扱い                       |
| ---- | ------------------------------------------------------------------------ | -------------------------- |
| 採用 | コードを読んで再現できる・筋が通る                                       | 直す                       |
| 却下 | 誤読・前提違い・プロジェクトの規約や設計文書と矛盾する                   | 理由を 1 行で残す          |
| 保留 | 設計・仕様の変更、`docs/` の決定の変更、運営判断が要る、直す範囲が大きい | 直さずユーザーに判断を仰ぐ |

前の周で却下・保留した指摘がまた出たら、調べ直さず同じ判定にする。

## 4. 直して検証する

- プロジェクトの規約（`CLAUDE.md` / `AGENTS.md`）に従う。バグの修正は先に再現するテストを書く。
- 周の終わりに、規約にある検証コマンド（型検査・テスト・整形）を実際に走らせ、通してから次の周へ進む。

## 5. 繰り返す・止める

次のどれかで止める。それ以外は 2 に戻る（N を 1 増やす）。

- 指摘が 0 件
- 新しい指摘がすべて却下・保留（採用して直したものが無い）
- 周回数の上限に達した（最後の周で直したものは Codex が見ていない。報告でそう書き、もう 1 周するか聞く）

## 6. 報告する

周ごとに「指摘 / 採用 / 却下（理由）/ 保留（判断してほしいこと）」を表にし、最後に検証コマンドの結果と、残った指摘・保留を書く。
`docs/` などの文書を直したら、それも書く。
コミット・push はしない。
